Three important architectural principles should govern the new application:

1. Keep comparison semantics out of the UI. Vue should display and control comparisons, not calculate them. CodeMirror should remain an editor and inspection surface, not the engine for comparing multi-gigabyte files.
2. Make large-file support a property of the entire system. Parsing, alignment, indexing, result persistence, pagination, rendering, cancellation, and export must all be bounded. Moving the existing browser code into a desktop window would not solve the underlying limitation.
3. Preserve existing JSON behavior before improving it. The documented identity matching, LCS, move detection, nested differences, ignore rules, and tolerance behavior need regression fixtures before the implementation is extracted, adapted, or replaced.

The JSON source repository itself was not included in the files I could inspect. The existing desktop PRD documents the browser prototype's behavior, but its exact implementation, dependencies, and memory characteristics remain subject to a source audit. The specifications below make that distinction explicit.

# JSON Compare Studio

## Product Documentation Index

## 1. Product overview

JSON Compare Studio is a local-first desktop application for comparing, inspecting, understanding, and validating JSON documents and large JSON datasets.

It is designed for developers, data engineers, analysts, QA teams, and technical users who regularly work with complex JSON structures.

The application should make both simple and advanced JSON comparison accessible through a polished desktop experience while remaining capable of processing datasets that exceed the practical memory limits of a browser application.

The application will provide:

- Side-by-side JSON comparison.
- Structural and semantic difference detection.
- Record identity detection and configurable matching.
- Nested object and array comparison.
- Added, removed, changed, moved, and unchanged record classification where objectively supported.
- Field-level difference navigation.
- Large-file inspection through bounded, virtualized views.
- JSON formatting, minification, sorting, cleanup, and repair preview.
- Ignore rules, regular expressions, and numeric tolerance.
- Search, filters, summaries, and detailed inspection.
- Exportable comparison reports.
- Saved comparison sessions and reusable profiles.
- Local processing without uploading source data.

## 2. Why we are building it

The existing browser-based JSON comparison application already provides a substantial user experience and a broad set of comparison capabilities.

However, a browser-based architecture creates practical constraints when processing very large datasets:

- Browser memory becomes a limiting factor.
- Large documents can block the main thread.
- Rendering complete documents becomes expensive.
- Large result collections are difficult to retain and navigate.
- Browser lifecycle and storage constraints complicate long-running operations.
- Processing, comparison, and presentation are too closely coupled.

The objective is not to rebuild the product as a desktop wrapper around the same browser workflow.

The objective is to move the comparison workload into a native local processing architecture, preserve valuable existing behavior, and redesign data access and rendering around large datasets.

## 3. Product principles

1. **Local-first:** Source files remain on the user's machine.
2. **Correctness first:** Comparison results must be deterministic, explainable, and testable.
3. **Bounded memory:** Source size and result count must not dictate frontend memory consumption.
4. **Progressive inspection:** Users retrieve only the records and values they need.
5. **Explicit semantics:** Matching, normalization, ignored values, and tolerance must be visible.
6. **No silent data changes:** Formatting and repair operations must not alter source files.
7. **Professional UX:** Complex functionality should remain discoverable without creating visual noise.
8. **Maintainable engineering:** Prefer simple, modular, well-tested implementation over unnecessary abstraction.
9. **Open source:** The product must not depend on internal XeroHome services, data, or business logic.
10. **Evidence-based performance:** Advertised file limits must come from repeatable benchmarks.

- `ARCHITECTURE.md`: Desktop runtime, JSON processing, algorithms, storage, and worker contracts.
- `UX_AND_IMPLEMENTATION.md`: Interface architecture, component standards, roadmap, QA, and contributor instructions.

## 5. Product boundary

This is an independent JSON utility application.

| `right_only`       | Property exists only on the right                 |

| `ignored`          | Difference was excluded by an active rule         |
| `ambiguous`        | Field comparison depends on unresolved alignment  |

## 3.3 Matching behavior

### Identity-based matching

The application should identify candidate identity fields by examining:

- Property names.
- Value types.
- Uniqueness.
- Presence on both sides.
- Sample overlap.
- Null and duplicate counts.

Candidate fields may include identifiers such as `id`, `uuid`, `key`, or domain-specific fields.

Automatic detection is advisory. The user must be able to review and confirm the selected identity.

Support:

- Single-field keys.
- Composite keys.
- Custom identity paths.
- Explicit matching configuration.
- Duplicate-key reporting.
- Null-key handling.
- Ambiguous-match reporting.

Do not assume that a property named `id` is always a valid identity.

### Positional matching

When identity is unavailable, positional matching may be appropriate for arrays whose order is meaningful.

The UI must make the selected strategy visible.

### Content-based matching

For identity-free arrays, the engine may use content hashes and similarity-based alignment to identify likely unchanged records and candidate changes.

It must not invent modified-record relationships where there is insufficient evidence.

When matching confidence is insufficient, report additions, removals, and ambiguity rather than presenting guesses as facts.

# 6. JSON parsing architecture

## 6.1 Parsing is not comparison

The parser should produce a representation suitable for incremental processing and comparison.

Avoid requiring a complete in-memory object graph for every input.

The parser should expose:

- Root type.
- Structure information.
- Object properties.
- Array boundaries.
- Record boundaries.
- JSON paths.
- Source byte offsets where reliable.
- Source line and column where available.
- Value type.
- Parse errors.

## 6.2 Input strategy

| Structure                      | Preferred strategy                                    |
| ------------------------------ | ----------------------------------------------------- |
| NDJSON                         | Stream one line or bounded record at a time           |
| Root array                     | Incremental array parser                              |
| Object with a large collection | Discover collection path and stream/index collection  |
| Nested arrays                  | Incremental traversal or disk-backed structural index |
| Small JSON document            | In-memory parse may be selected                       |
| Huge scalar or string          | Bounded processing with explicit resource limits      |

The engine must document where it materializes values.

A streaming parser does not automatically guarantee a streaming comparison. Alignment and matching can still require indexes.

## 6.3 Source preservation

The source file is authoritative.

Store source references such as:

- File identifier.
- Byte offset and length, when reliable.
- Array index.
- JSON path.
- Record reference.
- Parser metadata.

For selected record inspection, retrieve the relevant source segment rather than loading the complete file.

If the parser cannot reliably locate a value by byte offset, use an explicit alternative source reference. Never invent offsets.

# 7. Comparison algorithms

The application should use a strategy appropriate to the structure and available identity information.

## 7.1 Object comparison

For JSON objects:

- Compare properties by key, not serialized property order.
- Distinguish absent properties from explicit `null`.
- Detect type changes.
- Recursively compare nested objects.
- Compare arrays using the configured array strategy.
- Preserve original values for inspection.

Object-key order should normally be treated as presentation rather than semantic content. If users need textual or order-sensitive comparison, provide a separate mode.

## 7.2 Identity-based array alignment

When a reliable identity key exists:

1. Extract the configured identity.
2. Validate null and duplicate identities.
3. Build a left-side lookup or disk-backed index.
4. Process right-side records.
5. Locate corresponding left-side records.
6. Classify added, matched, changed, and removed records.
7. Determine positional movement separately from content changes.

For large datasets, use disk-backed indexes where an in-memory map exceeds the configured budget.

Composite keys must use unambiguous serialization. Do not concatenate arbitrary values with a delimiter that may occur inside those values.

## 7.3 Duplicate identity handling

Duplicates must never silently produce a Cartesian multiplication of candidate matches.

The engine should:

- Detect duplicate groups.
- Report group sizes.
- Match exact identical records within groups where the existing semantics permit.
- Preserve ambiguous candidate relationships.
- Apply a documented duplicate policy.
- Make unresolved matching visible to the user.

Do not silently select an arbitrary record and report it as a confident match.

## 7.4 Identity-free array alignment

The documented browser prototype uses a combination of:

- Exact LCS for small collections.
- Content-hash anchors.
- Similarity-based gap filling for larger collections.

These techniques should be retained only after source audit and parity testing.

A practical target design is:

1. Use exact LCS when collection sizes are below measured thresholds.
2. Use stable content hashes to find candidate anchors for larger arrays.
3. Use patience-style or LIS-based alignment where appropriate.
4. Apply bounded similarity matching to unresolved gaps.
5. Mark uncertain matches as ambiguous.
6. Fall back to additions and removals when confident alignment is not possible.

The thresholds must come from benchmarks. Avoid a fixed arbitrary array-size cutoff.

## 7.5 Move detection

Move detection should be independent from field-change detection.

A record can be:

- Unchanged and moved.
- Changed and moved.
- Unchanged and not moved.
- Added.
- Removed.

For identity-based records, movement can be derived from matched positions.

For identity-free arrays, movement may be uncertain. The engine must not claim a move when the alignment is ambiguous.

## 7.6 Hashing

Content hashing can reduce expensive comparisons, but hash equality must not be the only correctness guarantee.

Recommended approach:

- Canonicalize values according to explicit comparison semantics.
- Hash canonical representations.
- Use hashes to identify likely equal records.
- Verify candidate matches when required.
- Preserve collision-safe correctness.

Canonicalization must explicitly define handling of:

- Object key order.
- Number representation.
- Unicode.
- Missing versus null.
- Array order.
- Ignored properties.
- Tolerance.

Do not use a single canonicalization policy for every comparison mode.

## 7.7 Numeric comparison

Preserve JSON number precision according to the parser and engine's supported representation.

Do not convert arbitrary high-precision numbers into JavaScript floating-point values and assume exactness.

Use exact numeric representations or decimal arithmetic where necessary.

Tolerance comparison should preserve original values and record the applied threshold.

- Retrieve field differences.

- Stream exports.
- Delete retained results.

# 10. Worker and job lifecycle

The worker runs independently of the Vue rendering thread.

Job lifecycle:

```
created
  -> inspecting
  -> validating
  -> running
  -> finalizing
  -> completed

running
  -> cancelling
  -> cancelled

running
  -> failed

running/finalizing after crash
  -> interrupted
  -> recovered or abandoned
```

Persist job metadata and state transitions.

## Progress events

The worker should report:

- Job ID.
- State.
- Processing phase.
- Bytes read and total bytes when known.
- Records processed and total records when known.
- Throughput.
- Elapsed time.
- ETA when meaningful.
- Memory use when measurable.
- Temporary disk use.
- Warnings and errors.

Unknown values must be represented as unknown, not fabricated.

## Cancellation

- Cancellation is cooperative.
- The UI immediately indicates that cancellation was requested.
- The worker checks cancellation at safe checkpoints.
- The worker confirms when it has stopped.
- Partial exports are not committed.
- Temporary artifacts are cleaned or marked for recovery.
- The UI must not report cancellation as complete before worker confirmation.

## Concurrency

Begin with one heavy comparison job at a time per application instance.

Support multiple lightweight operations such as result browsing and metadata inspection where safe.

Introduce concurrent comparisons only after resource isolation and performance testing.

# 11. Desktop communication protocol

Use a versioned protocol between the desktop application and the processing worker.

The protocol should define:

- Handshake and version negotiation.
- Worker health.
- Start job.
- Cancel job.
- Progress event.
- Query summary.
- Query results.
- Query record detail.
- Export request.
- Export progress.
- Shutdown.
- Structured errors.

Use JSON Schema or an equivalent runtime validation approach.

The frontend must not receive raw multi-gigabyte content through Tauri IPC.

For large values, use file-backed references and bounded retrieval operations.

The protocol should include stable error codes and avoid leaking stack traces to the UI.

# 12. Storage and recovery

Use a per-user application workspace with job-specific directories.

```
application-data/
├── sessions/
├── results/
├── workspace/
│   └── job-id/
│       ├── indexes/
│       ├── temporary/
│       ├── staged-exports/
│       └── manifest.json
└── logs/
```

The actual directory layout may change with implementation.

Cleanup rules:

- Successful job: retain result data according to retention settings; remove disposable intermediates.
- Cancelled job: remove partial results unless checkpoints are explicitly supported.
- Failed job: retain useful diagnostics, remove unsafe partial outputs.
- Interrupted job: inspect committed state and offer recovery or deletion.
- Disk pressure: stop safely before publishing incomplete results.

Never claim secure deletion on SSDs or filesystems where it cannot be guaranteed.

# 13. Export architecture

Exports must be generated from canonical result storage.

Requirements:

- Stream records to disk.
- Support all differences and filtered differences.
- Include a summary and configuration metadata.
- Stage output in a temporary file.
- Commit only after successful completion.
- Support cancellation.
- Remove partial output after failure.
- Prevent overwriting source files.
- Confirm destination collisions.
- Report final file location and export status.

# 14. Security boundaries

Tauri:

- Expose only required commands.
- Restrict capabilities.
- Validate filesystem paths.
- Use restrictive permissions for temporary files.
- Avoid unnecessary shell execution.

Worker:

- Validate requests.
- Validate paths and options.
- Limit resource consumption.
- Avoid logging source values.
- Handle malformed JSON safely.
- Protect against regex denial of service.

Frontend:

- Treat JSON values as untrusted data.
- Never render input as executable HTML.
- Avoid unsafe HTML injection.
- Display large strings through bounded rendering.

## Important architectural recommendations

These are the decisions I would keep firm before implementation starts.

1\. Do not automatically rewrite the existing JSON engine.

The current PRD documents ID-based patience/LIS alignment, LCS for smaller collections, and hash-based matching for larger collections. These are useful existing capabilities, but we need to inspect the actual implementation and establish parity before deciding whether to retain, extract, or replace them.

2\. Treat JSON parsing and JSON comparison as separate engineering problems.

A parser that reads a 5 GB file incrementally does not automatically solve matching. Identity indexes, array alignment, duplicate handling, and result persistence can still consume substantial memory and disk. Benchmark these independently.

3\. Do not use CodeMirror as the large-file viewer.

Keep CodeMirror for editing and selected excerpts. Use a virtualized JSON tree and structured comparison viewer for large datasets.

4\. Make the result repository part of the initial architecture.

Do not wait until the results screen becomes slow before introducing disk-backed storage. The comparison engine should produce canonical results incrementally, and the UI should query those results.

5\. Keep the open-source boundary clean.

Reuse architectural knowledge and independently reusable code only after checking ownership and licenses. No internal XeroHome data, private infrastructure, proprietary business modules, or internal CSV merge/export features should enter the public project.
